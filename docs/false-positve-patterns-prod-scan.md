# Prod-Mode Scan False-Positive Patterns

**Purpose:** Catalogue known false-positive patterns in the prod-mode website scanner to avoid flagging non-issues during outreach calls. Update as new patterns are discovered.

---

## Category P2 — Exposed JS Dependencies / Asset Timestamps

### FP-001: Page-Builder CSS Selectors as Unix Timestamps

**Observation:** The scanner regex `[1-9][0-9]{9}` matches 10-digit Unix timestamps in asset URLs. However, page builders (WPBakery, Elementor, Divi, Oxygen) frequently generate CSS selectors that happen to be 10-digit numbers and are indistinguishable from timestamps by pattern alone.

**Discovered:** Bloom Digital — `#gap-1326761003` (Jan 2012), `#gap-1724681379` (Aug 2024), `#gap-1777765399` (May 2026). All three were `#gap-{number}` CSS selectors generated by a page builder, not build timestamps.

**Impact of FP:** Would incorrectly claim ~2-year or ~14-year asset staleness, severely damaging credibility on an outreach call.

**Detection:** Check context — if the regex match appears inside a `#gap-`, `#row-`, `#col-`, `#section-`, `#wrapper-`, `#box-`, or similar page-builder ID selector, it is not a valid timestamp. Also check if the number appears as a CSS class like `.gap-1234567890`.

**Fix for scanner:** Before reporting a timestamp finding:
1. Extract 5 lines of context before and after the match
2. If the match is enclosed in `#<name>-NUMBER` or `.<name>-NUMBER` where `<name>` is a common page-builder keyword (gap, row, col, section, column, inner, wrapper, box, pad, margin, overlay), skip it
3. Only report if the timestamp is in a `src`, `href`, or filename context (e.g., `/assets/main.1674106587.js`, `style.css?ver=1674106587`)

### FP-002: Cache-Buster Query Parameters vs Build Timestamps

**Observation:** `ver=1234567890` query parameters on CSS/JS files can be either:
- A true Unix build timestamp (`?ver=1674106587` = Jan 2023)
- A random/hashed version string that happens to be numeric (`?ver=123456789`)

WordPress often uses `?ver=6.4.2` (semver) but plugins may generate numeric version strings that are not timestamps.

**Detection:** `date -d @TIMESTAMP` should produce a date within the past 5 years. If the date is in the future or before 2005, it is not a real timestamp. Cross-check: does the same number appear on multiple unrelated assets? If yes, it is likely a version hash, not a build timestamp.

### FP-003: `jquery-migrate` Mistaken for `jquery` Core

**Observation:** The scanner regex `jquery[^"']*[0-9]+\.[0-9]+\.[0-9]+` matches both `jquery` core and `jquery-migrate` plugin. jQuery Migrate is a WordPress compatibility plugin — its version number is independent of jQuery core's and does not carry the same CVEs.

jQuery Migrate 3.4.1 is the **current stable** version and is NOT affected by CVE-2020-11022 or CVE-2020-11023 (those affect jQuery core <3.5.0, not the migrate plugin).

**Discovered:** Perth Sites, Perth Website Studio, Oliver Agency, Loaded Communications — all had `jquery-migrate.min.js?ver=3.4.1` flagged as "jQuery 3.4.1 with known XSS CVEs".

**Impact of FP:** Would incorrectly accuse an agency of running a vulnerable jQuery version when they're running the current migrate plugin. Destroys credibility on outreach.

**Detection:** Before reporting a jQuery version:
1. Check if the matched string is `jquery-migrate` — if so, skip (it's the WordPress compatibility plugin, not jQuery core)
2. Only flag if the match is for `jquery.min.js`, `jquery.js`, or `jquery.core.js` (the actual jQuery library)
3. Check the full URL path: `/ajax/libs/jquery/X.Y.Z/` on CDNs = jQuery core. `/wp-includes/js/jquery/jquery-migrate` = migrate plugin

### FP-004: CDN Version Strings That Look Stale but Are Correct

**Observation:** A site may intentionally serve an older major version of a library (e.g., jQuery 1.x for legacy plugin compatibility). This is not necessarily a security issue if:
- The library version is still receiving security patches (unlikely for jQuery 1.x)
- The vulnerability is not exploitable via the specific usage pattern on the site

**Detection:** Do not flag a library version without checking CVE status. jQuery <3.5.0 = real XSS CVEs. Angular 1.x = real CVEs. But a library pinned to a specific version for compatibility should be noted as a "dependency freeze" rather than outright negligence.

## Category P1 — Technology Stack Fingerprinting

### FP-005: WAF That Is Actually a CDN

**Observation:** The scanner treats `server: cloudflare` as a WAF detection. Cloudflare is primarily a CDN — having Cloudflare does not mean the customer has enabled the WAF/security features (rate limiting, bot management, WAF rules). Many sites use Cloudflare purely for caching.

**Detection:** Check for WAF-specific headers like `cf-waf-error`, `x-sucuri-id`, `x-wordfence-*`, or response codes 403/406 with WAF-specific body text. `server: cloudflare` alone is not sufficient to conclude a WAF is active.

### FP-006: WAF That Is Actually a CDN

**Observation:** The scanner treats `server: cloudflare` as a WAF detection. Cloudflare is primarily a CDN — having Cloudflare does not mean the customer has enabled the WAF/security features (rate limiting, bot management, WAF rules). Many sites use Cloudflare purely for caching.

**Detection:** Check for WAF-specific headers like `cf-waf-error`, `x-sucuri-id`, `x-wordfence-*`, or response codes 403/406 with WAF-specific body text. `server: cloudflare` alone is not sufficient to conclude a WAF is active.

### FP-007: `X-Powered-By: WP Engine` as Info Leakage

**Observation:** WP Engine sets `X-Powered-By: WP Engine` on all hosted sites. This is the hosting provider, not a technology-version disclosure. It does not provide CVE-mappable information.

**Detection:** Treat `X-Powered-By: WP Engine` as hosting-provider identification, not version disclosure. Only flag as P6 information leakage if the value includes a version (e.g., `PHP/8.1.2`).

## Category P3 — TLS & Encryption

### FP-008: HSTS `max-age=0` vs Missing HSTS

**Observation:** `Strict-Transport-Security: max-age=0` means HSTS is being explicitly **disabled** by the server. This is different from a completely missing HSTS header. The site may have HSTS configured but be serving a `max-age=0` during maintenance.

**Detection:** Treat `max-age=0` as equivalent to "no HSTS" for reporting purposes, but note it as "HSTS explicitly disabled" rather than "HSTS missing" — this is actionable feedback (someone went out of their way to turn it off).

### FP-009: Self-Signed Certificate on Dev/Staging Subdomain

**Observation:** Scanning a production site may reveal a self-signed or expired certificate on a sibling subdomain discovered via DNS. This is common for staging/dev environments and is not a production finding.

**Detection:** Check if the hostname contains `staging`, `dev`, `test`, `uat`, or similar. If so, downgrade severity or exclude.

## Category P4 — Authentication Protocol Exposure

### FP-010: `wp-json/wp/v2/users` Returning 401 vs 200

**Observation:** A 401 response on `/wp-json/wp/v2/users` means the endpoint exists but requires authentication — this is acceptable posture. A 200 response with user data is the actual finding. The scanner should distinguish between:
- 200 = exposed (🔴 Critical)
- 401/403 = endpoint exists but blocked (🟡 Medium — note as "protected but present")
- 404 = endpoint disabled or not WordPress (✅ Pass)

**Discovered:** The Start (200 — exposed users). Oliver Agency (200 — exposed users). Lilo (401 — protected). Bloom Digital (401 — protected).

### FP-011: `readme.html` 200 on WordPress Sites

**Observation:** `readme.html` returning 200 is very common. Many high-profile WordPress sites (including major brands) leave this file accessible. While technically information leakage, the risk is low — WordPress version can be determined through many other channels. The real finding is the **combination** of readme access + exposed users + no WAF, not the readme alone.

**Detection:** Flag readme access only when combined with other findings. A standalone readme.html is 🟡 Medium at most.

## Category P5 — HTTP Security Headers

### FP-012: CSP `upgrade-insecure-requests` as "Minimal"

**Observation:** `Content-Security-Policy: upgrade-insecure-requests` is not useless — it forces all HTTP resources to be upgraded to HTTPS. However, it does nothing to prevent XSS. The scanner should distinguish between:
- "CSP missing entirely" (🔴 on sites with user-generated content)
- "CSP set to upgrade-insecure-requests only" (🟡 Medium — provides HTTPS enforcement but no XSS mitigation)
- "CSP with unsafe-inline/eval" (🟠 High — effectively no protection)
- "CSP with nonces/hashes" (✅ Good)

### FP-013: `Access-Control-Allow-Origin: *` on Static Assets

**Observation:** CDN-hosted static assets (fonts, images, JS libraries) commonly set `Access-Control-Allow-Origin: *` intentionally — this is required for cross-origin font loading and is not a security issue.

**Detection:** Check if the response is for a static asset (JS/CSS/font/image) rather than the main HTML page. If so, `Access-Control-Allow-Origin: *` is expected and not a finding. Only flag it on the main document or API response.

**Discovered:** PWD (pwd.com.au) — `access-control-allow-origin: *` was set on the main document response. This is a genuine finding, not a FP.

## Category P6 — Information Leakage

### FP-014: Comment Timestamps vs Asset Timestamps

**Observation:** HTML comments often contain dates in `YYYY-MM-DD` format, or Unix timestamps in data attributes for JavaScript functionality. These are content timestamps, not asset pipeline timestamps.

**Detection:** Only treat 10-digit numbers as build timestamps if they appear in:
- Filename patterns: `/assets/name.1234567890.js`, `/build/1234567890.js`
- Query parameters: `?ver=1234567890`, `?t=1234567890`, `?timestamp=1234567890`
- Version strings: `v=1234567890`

Skip if the number appears in:
- CSS selectors (`#gap-1234567890`, `.row-1234567890`)
- HTML comments containing dates
- data- attributes (`data-id="1234567890"`)
- Content text (article IDs, order numbers, etc.)

### FP-015: Google Analytics / Tag Manager as "Third-Party Dependency"

**Observation:** GA/GTM scripts are nearly universal. Their presence in CDN/third-party script lists should not be flagged — they are analytics, not application dependencies. However, note that GTM can be used to inject arbitrary scripts if the GTM account is compromised.

**Detection:** Exclude `googletagmanager.com`, `google-analytics.com`, `facebook.net`, and similar ad/analytics domains from the "exposed third-party dependencies" finding, unless they contain version strings linking to known-vulnerable libraries.

## Category P7 — AI-Era Threat Assessment

### FP-016: `api.openai.com` in Client-Side JS That Is Behind a Backend Proxy

**Observation:** The scanner may flag `fetch('https://api.openai.com/v1/chat/completions')` in client-side JavaScript as a direct browser-to-LLM call. However, if this string appears in a `.js.map` source map (development artifact) rather than the actual production bundle, it may be a backend proxy pattern that was incorrectly included in the source map.

**Detection:** Check if the match is in a `.js.map` file vs a `.js` file. Source map findings are P6 (source map exposure), not P7 (direct API calls). If the API key pattern `sk-proj-` appears in a source map but not in the production bundle, it is a source-map exposure finding, not an API-key exposure finding.

### FP-017: Generic `/api/chat` Endpoints That Are Not AI-Related

**Observation:** Many non-AI applications have `/api/chat` endpoints for traditional live chat (e.g., Intercom, Zendesk, Olark). The endpoint name alone is not sufficient to conclude AI integration.

**Detection:** Check for AI-specific indicators: presence of LLM SDKs (`openai`, `anthropic`, `langchain`), AI-specific headers, or API key patterns. A standalone `/api/chat` with a human-support widget is not an AI-era finding.

## Summary: Scanner Anti-Patterns

| Anti-Pattern | Root Cause | Prevention |
|-------------|------------|------------|
| Treating `#gap-N` as Unix timestamp | Page-builder CSS selectors match timestamp regex | Add context-aware filtering (skip CSS-ID context) |
| Treating any `ver=N` as build timestamp | Version hashes indistinguishable from timestamps | Validate with `date -d @N`, reject future/pre-2005 dates |
| Treating Cloudflare as WAF | CDN ≠ WAF | Check for WAF-specific headers/status codes |
| Treating all 401/403 on `wp-json/users` as good | 401 is protected, but endpoint still exists | Distinguish 200 vs 401/403 vs 404 |
| Flagging GA/GTM as third-party risks | Almost universal, rarely part of app dependency tree | Explicitly exclude from dependency findings |
| Flagging static-asset CORS `*` as finding | Required for fonts/CDN, not a security gap | Only flag on main document or API endpoints |
